## 1. PROJECT OVERVIEW

**Project Name:** KRMU Campus Intelligence Platform

**What it is:** A web application for a university campus that lets students submit feedback and grievances (complaints), automatically analyzes that feedback with NLP, routes grievances to the right staff with SLA (deadline) tracking, sends real-time notifications, logs every important action for auditing, and gives admins a Power BI–integrated analytics dashboard on how the campus is performing.

**Scope — read carefully:**
- This is a **web-only application**. There is no mobile app.
- It is **one single web application** built in React.js. Students, staff, and admins all use the same app — what they see and can do changes based on their role (role-based views), not separate apps.
- The backend is a single FastAPI service talking to one PostgreSQL database.

**Core Modules:**
1. Identity & Role-Based Access Control (RBAC)
2. Campus Structure (Departments, Categories, Facilities, Transport)
3. Student Feedback + NLP Sentiment/Topic Analysis
4. Grievance Management + SLA Tracking + Status Updates
5. Notifications (real-time, via Firebase Web Push)
6. Audit Logging (for security and compliance)
7. Power BI–Integrated Analytics & Operational Intelligence Layer
8. Data Import module (Attendance, Exam Schedule, Facility Usage, Feedback, Transport)
9. One React.js web app containing the Student Portal, Staff Portal, and Admin Dashboard, each shown based on the logged-in user's role

## 6. CORE USER WORKFLOWS

### 6.1 Student Feedback Flow
```
Student logs in → goes to Dashboard → submits Feedback (text + rating, optionally anonymous)
   → NLP analyzes it (sentiment, keywords, topics, severity) → result saved in feedback_analysis
   → Result becomes visible in Analytics
```
If NLP fails, see Section 11.6 — feedback submission must still succeed.

### 6.2 Student Grievance Flow
```
Student submits a Grievance (title, description, category)
   → System detects priority and auto-assigns it to the right department
   → SLA timer starts (deadline depends on sla_policies for that priority)
   → Staff works on it and resolves it (every status change is logged in grievance_updates)
   → Student reviews the resolution:
        - Accepts it → Grievance is Closed
        - Rejects it → Grievance is Reopened → a NEW SLA cycle starts → goes back to Staff
   → Student is notified at every status change
   → If the SLA deadline is missed, an escalation notification is triggered automatically
```

---

## 7. GRIEVANCE STATUS TRANSITION RULES

The AI must enforce these exact transitions in the backend. No other status change is allowed. Any attempt to make an invalid transition must be rejected with a `409 Conflict` error.

| Transition | Who is allowed to perform it |
|---|---|
| `open` → `in_progress` | Assigned Staff, or Admin |
| `in_progress` → `resolved` | Assigned Staff, or Admin |
| `resolved` → `closed` | Student (the grievance owner), or Admin |
| `resolved` → `reopened` | Student (the grievance owner) only |
| `reopened` → `in_progress` | Assigned Staff, or Admin |
| `closed` → anything | Not allowed. `closed` is final in v1. (Admin override, if ever needed, is a v2 decision — do not build it now.) |

Every transition — valid or attempted-and-rejected — should still be logged appropriately: valid transitions go into `grievance_updates`; rejected attempts should just return the error and are not logged as a status change.

## 8. SLA ENGINE SPECIFICATION

### 8.1 Default SLA durations (seeded into `sla_policies`, editable later by Admin)

| Priority | SLA Duration |
|---|---|
| Urgent (Critical) | 4 hours |
| High | 24 hours |
| Medium | 72 hours (3 days) |
| Low | 120 hours (5 days) |

### 8.2 Warning and breach behavior
- **Warning** triggers when **80%** of the SLA duration has elapsed (`sla_policies.warning_percentage = 80` by default). At this point, `sla_events.status` becomes `warning` and a notification is sent to the assigned staff and the department HOD.
- **Breach** triggers the moment `deadline_at` passes with the grievance not yet resolved. `sla_events.status` becomes `breached`, `breached_at` is set, and `operational_metrics.sla_breaches` reflects it in the next aggregation run.
- **On breach, notify:** the assigned staff, the department HOD, and the Admin (all three, via in-app + push notification).

### 8.3 Other SLA rules (explicit, do not guess)
- **SLA is never paused** in v1. The clock runs continuously from `started_at` to `deadline_at` regardless of weekends, holidays, or staff availability.
- **A resolved grievance stops its SLA.** The moment status becomes `resolved`, set `sla_events.completed_at = resolved_at` and `sla_events.status = completed`. No further breach checks run on it.
- **A reopened grievance creates a brand-new `sla_events` row** (a new SLA cycle starts from the moment it's reopened, using the same `sla_policies` priority). The original `sla_events` row is kept as-is for audit/history — do not delete or overwrite it.

## 10. DATA IMPORT SPECIFICATION

The Admin-only data import feature is not a generic file uploader. It supports exactly these **five** import types, each mapped to `data_imports.data_type`:

1. **Attendance**
2. **Exam Schedule**
3. **Facility Usage**
4. **Feedback**
5. **Transport**

### Import workflow (must be built exactly in this order)
```
Upload file (.csv or .xlsx)
   ↓
Validate (check required columns exist, check data types, check foreign keys resolve)
   ↓
Preview (show the admin a sample of parsed rows + validation results before committing)
   ↓
Import (admin confirms → rows are inserted)
   ↓
Reject invalid rows (valid rows are still imported; invalid ones are skipped, not the whole file)
   ↓
Generate import report (total_records, successful_records, failed_records, error_report listing exactly which rows failed and why)
```
Every import run creates one `data_imports` row tracking this whole lifecycle.

## 11. NLP REQUIREMENTS (Feedback Analysis)

### 11.1 What it must do
1. **Sentiment Analysis** — classify each feedback as positive, neutral, or negative, with a confidence score
2. **Keyword Extraction** — pull out the important words/phrases (saved as JSONB)
3. **Topic Modeling** — detect recurring themes across many feedback entries (saved as JSONB)
4. **Severity Detection** — flag strongly negative feedback so it can be escalated
5. **Language Detection** — should handle both English and basic Hindi feedback

### 11.2 Implementation constraints
- Use **lightweight, free, open-source Python libraries only** (e.g. spaCy, scikit-learn, NLTK, TextBlob, VADER). 
- **Do not call any paid external AI API** (OpenAI, Anthropic, Google Cloud NLP, AWS Comprehend, etc.) unless the user explicitly approves it first.
- The first implementation (v1) should include: text preprocessing (cleaning, tokenization) → sentiment classification → keyword extraction → basic topic modeling → severity classification, all running locally in the Python backend.

### 11.3 How it runs
Immediately after a student submits feedback, kick off the analysis using FastAPI's `BackgroundTasks` (no separate worker process, no Celery, no Redis) — write the result into `feedback_analysis` once done.

### 11.4 NLP failure handling — explicit, do not guess
```
Feedback submitted
       ↓
Feedback row is saved successfully (status = "submitted") — this always succeeds
       ↓
NLP background task runs
       ↓
   If it fails:
       feedback_analysis.analysis_status = FAILED
       feedback_analysis.error_message = <captured error>
       feedback.status = "analysis_failed"
       error is logged (structured log, and ideally an audit_logs entry)
       ↓
   If it succeeds:
       feedback_analysis.analysis_status = COMPLETED
       feedback.status = "analyzed"
```
**A feedback submission must never fail or be rejected just because the NLP step failed or is slow.** The student always gets a successful "Feedback submitted" response the moment the `feedback` row is saved — NLP happens after, in the background, and its failure is invisible to the student (visible only to Admin, who can see `analysis_status = FAILED` entries and optionally retry).

- Total Feedback

### 12.3 Operational Gap Score — exact formula

Do not guess this. Use the following formula and weights for v1 (they can be tuned later by the user, but the AI must implement exactly this to start):

```
Gap Score =
    (NegativeSentimentScore   × 0.20) +
    (SLABreachRate            × 0.25) +
    (ResolutionDelayScore     × 0.20) +
    (GrievanceVolumeScore     × 0.15) +
    (DissatisfactionScore     × 0.20)
```

Where each component is a 0–100 value, calculated per department per period as:

| Component | Formula |
|---|---|
| `NegativeSentimentScore` | `(negative_feedback / total_feedback) × 100` (0 if `total_feedback` is 0) |
| `SLABreachRate` | `(sla_breaches / total_grievances) × 100` (0 if `total_grievances` is 0) |
| `ResolutionDelayScore` | `min(100, (avg_resolution_minutes / sla_target_minutes_for_period) × 100)` — compares actual average resolution time against the SLA target duration for that priority mix |
| `GrievanceVolumeScore` | `(this department's total_grievances / the highest total_grievances among all departments in the same period) × 100` |
| `DissatisfactionScore` | `100 − student_satisfaction` (since `student_satisfaction` is already stored as a 0–100 percentage) |

**Result bands:**
| Gap Score | Label |
|---|---|
| 0–30 | Low |
| 31–60 | Moderate |
| 61–80 | High |
| 81–100 | Critical |

The final `gap_score` written to `operational_metrics` should be rounded to 2 decimal places.

## 14. API RESPONSE, PAGINATION & ERROR STANDARDS

### 14.1 Standard error format
Every error response across the whole API must follow this exact shape:
```json
{
  "success": false,
  "error": {
    "code": "GRIEVANCE_NOT_FOUND",
    "message": "The requested grievance does not exist."
  }
}
```

### 14.2 Standard HTTP status codes to use
| Code | Meaning |
|---|---|
| 400 | Bad Request / general validation error |
| 401 | Unauthorized (not logged in / invalid token) |
| 403 | Forbidden (logged in, but wrong role/permission) |
| 404 | Not Found |
| 409 | Conflict (e.g. an invalid grievance status transition) |
| 422 | Validation Error (Pydantic schema failure) |
| 500 | Internal Server Error |

### 14.3 Standard pagination format
Apply this to **every** list endpoint: `/feedback`, `/grievances`, `/users`, `/notifications`, `/audit-logs`.

Request:
```
GET /grievances?page=1&page_size=20
```

Response:
```json
{
  "items": [],
  "page": 1,
  "page_size": 20,
  "total": 1250,
  "total_pages": 63
}
```
Never return an entire table's worth of rows in one unpaginated response.

### 14.4 Search & filter requirements

**Grievances** must support filtering by: `status`, `priority`, `department`, `category`, `assigned_staff`, `date range`, `SLA status`. Also support sorting by `created_at` and searching by `title`/`ticket_number`.

**Feedback** must support filtering by: `category`, `sentiment`, `rating`, `date range`, `department`, `severity`.
